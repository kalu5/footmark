# Spec

“Spec”是“Specification”（规格、规范）的缩写，但它具体指什么，取决于你所在的领域和上下文。它既可以是一份描述产品“应该是什么样”的文档，也可以是一种特定格式的文件，还可以是一个权威组织的名字。

## Spec在不同场景下的具体含义和用法

### 📄 作为“文档”：软件世界的蓝图

这是“spec”最核心的用法，它是一份详细说明产品功能、行为或设计的文档，在整个软件开发生命周期中扮演着关键角色。其核心目标是在团队内部（如产品经理、开发、测试）建立共识，确保所有人对“要构建什么”有一致的理解，从而避免因理解偏差导致的返工。

#### Spec文档通常分为两大类：

- 功能规格说明书 (Functional Spec)：从用户的角度出发，把软件当成一个“黑盒子”，主要描述外部功能、用户交互、输入输出、界面和边界条件等。

- 技术规格说明书 (Technical Spec) / 设计文档：从开发者的角度出发，把软件当成一个“透明箱子”，主要描述内部的设计、架构、算法、数据库结构等技术实现细节。


#### 一份高质量的Spec文档通常具备以下特点：

- 清晰的定义：明确定义所有涉及的核心概念。

- 明确的目标：清晰阐述功能的目标和成功的标准。

- 详尽的步骤：提供从开始到结束的、无歧义的操作步骤。

- 考虑边界和异常：明确各种边界条件（如极限值、空值）和异常情况的处理方式。

- 列出假设：说明在设计时所做的各种前提假设。

- 指出副作用：诚实地说明功能可能带来的副作用或风险。


#### 在AI领域，Spec同样至关重要，具体体现为：

- 模型规格 (Model Specification)：详细说明模型的架构（如Transformer）、参数规模（如7B、70B）、输入输出格式等。

- API规范 (API Specification)：定义AI服务的接口，如使用OpenAPI、gRPC等格式，明确端点、请求/响应结构、认证方式等。

- 数据格式规范 (Data Specification)：规定训练和推理数据的格式、预处理方式和验证规则。

### 💾 作为“文件格式”：特定软件的配置文件

在某些领域，“.spec”是一种特定的文件格式。

- RPM规范文件：在Linux系统中，.spec文件是rpmbuild工具用来构建RPM软件包的指令文件。它是一个文本文件，包含了软件包的名称、版本、源代码位置、安装和编译指令等信息。

- 光谱数据文件：在科研领域，.spec文件常用于存储光谱数据，是一种简单的文本格式，可以包含一个或多个“扫描”的数据集。

### 🏢 作为“组织”：性能评测的权威机构

- SPEC (The Standard Performance Evaluation Corporation) 是一个全球性的、非营利的标准性能评估组织。它由众多知名高校、研究机构和IT企业（如斯坦福、清华、微软等）共同组成。

- SPEC的核心工作是开发和维护一套标准化的基准测试程序（Benchmark），用于客观、公正地评估计算机系统的性能。其测试结果在业界具有很高的权威性，常被用作硬件采购和选型的参考。


## Vibe Coding Spec

- 在Vibe Coding（氛围编程）中，spec（规格说明书）是你用来驯服AI创造力、确保项目不跑偏的“锚点”和“安全绳”。

- 简单来说，纯Vibe Coding是“想到什么说什么，让AI自由发挥”，而引入spec后，则转变为“先规划，再执行”的Spec-Driven Development（规范驱动开发，简称SDD）。

### 🤔 为什么要用 Spec？解决Vibe Coding的痛点

- 纯Vibe Coding在项目初期非常爽快，但随着项目变复杂，问题会接踵而至。Spec正是为了解决这些痛点而生：

- 解决“上下文腐烂” (Context Decay)：长对话中AI会遗忘早期需求，导致开发跑偏。Spec文档作为固定“锚点”，锁定了核心需求，即使开启新对话，AI也能快速恢复上下文。

- 应对“审查瘫痪” (Review Paralysis)：AI生成大量代码，人工难以逐行审查。我们只需审查Spec文档（描述“做什么”）而非具体代码（“怎么做”），工作量大大减少。

- 消除“维护断层” (Maintenance Gap)：数月后，面对AI生成的陌生代码且无文档，难以维护。Spec文档本身就是一份清晰、可读的“活文档”，记录了设计意图，方便后续维护。

### 📝 如何在Vibe Coding中使用 Spec？

将Spec融入Vibe Coding，本质是在“自由发挥”和“严谨规划”间找到平衡。一个典型的Spec驱动开发工作流包含以下步骤：

1. 起草Spec (Drafting)：向AI清晰描述你的功能需求。关键是让它产出结构化的Spec文档，而非直接写代码。

- Prompt示例：“请为‘用户登录’功能撰写一份Spec。需包含：功能目标、用户操作步骤、输入/输出、异常处理、验收标准。”

- Spec文件示例：docs/specs/user-login.spec.md。一份好的Spec可以包含PRD (产品需求文档)、技术设计和任务列表 (Task List)。

2. 签署Spec (Sign-off)：审阅AI生成的Spec，确认无误后“签署”同意。这一步非常关键，相当于确认了最终“蓝图”。后续AI将严格依此执行。

3. 规划任务 (Plan)：让AI根据已签署的Spec，将开发工作拆解成具体的、可执行的步骤或任务列表，并更新到文档中。

4. 执行开发 (Execute)：现在，可以指示AI严格按照Spec文档和任务列表来编写代码了。

- Prompt示例：“请根据 docs/specs/user-login.spec.md 中的Spec和任务列表，开始执行任务1.1。”

5. 审查与迭代 (Review & Iterate)：实现完成后，开启一个全新的对话（或更换模型）来审查代码和Spec，避免上下文干扰。如有新需求或调整，回到第一步更新Spec，再继续开发。

### 🛠️ 实用工具与技巧

使用“Spec Mode”：许多AI编程工具支持“Spec Mode”，它会强制AI在编码前先进行研究和规划。

- Claude Code: 可将spec-mode.md放入~/.claude/commands/，然后使用 /spec-mode plan this feature: <描述你的功能> 指令。

- VS Code: 可通过命令面板创建新的“Spec”模式文件。

参考现成工作流：可以借鉴社区已有的成熟实践，例如 `superpowers` 或 `vibe-coding-tutorial` 等项目中关于Spec驱动的开发流程。

核心原则：Spec是源头：牢记 Spec是“真理之源” (Source of Truth)。代码可以随时重写，但Spec定义了核心意图，是项目的稳定基石。

从纯粹的“Vibe”到引入“Spec”，核心是将你的意图（Intent）清晰地传递给AI。这会让你从一个被动的“验收者”，转变为一个主动的“架构师”和“产品经理”，实现更可控、更高质量的AI辅助开发。
