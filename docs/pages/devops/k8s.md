# K8s(Kubernetes)

- 开源容器编排平台，用来管理Docker等容器
- 容器的调度中心+管家+监控室，
- 官方定位：自动化部署、扩缩容、管理容器化应用的平台

## 传统部署的缺点

- 应用挂了不能自动重启，需要人工处理
- 访问量突增，无法快速扩容
- 多台服务器部署复杂，环境不一致
- 迁移、升级应用麻烦，容易出错
- 资源利用率低，服务器浪费严重

## K8s解决的核心问题

1. 自动故障恢复
应用崩溃、服务器宕机，k8s会自动在其他节点重启容器
2. 自动扩缩容
根据访问压力，自动增加/减少实例数量，不用人工干预
3. 统一调度与管理
多台服务器统一管理，像管理一台机器一样方便
4. 服务自愈与高可用
自动检查健康状态，不健康就杀掉重建，保证服务稳定
5. 环境一致性
基于容器，开发、测试、生产环境安全一致，避免只是本地能运行
6. 滚动更新与回滚
升级应用不停机，出问题一键回滚，安全可靠

## 适用场景

1. 微服务架构
2. 多服务器集群
3. 需要高可用、自动运维业务
4. 频繁发布、迭代快的项目

## 核心组件

Deployment -> 管理Pod(创建/扩容/更新/回滚) -> Service(固定访问入口)
经理        ->  服务员                   -> 门牌号

- Pod(最小部署单元)
  - 核心定义：k8s中最小的部署和调度单元，不是容器本身，而是容器的包装器，一个Pod可以包含多个容器（通常1个），这些容器共享同一网络、存储资源
  - 基础要点
    - k8s不会直接调度容器，只会调度Pod(所有的容器必须住在Pod中，才能被K8s管理)
    - Pod内的容器同生死，一个容器崩溃、异常，整个Pod会被k8s杀掉，重新创建
    - 每个Pod有独立的IP地址（仅在K8s集群内可用，外部无法直接访问）
- Service（Pod的固定访问入口）
  - 核心定义：k8s中的一种资源，用来暴露Pod的固定访问入口，外部可以通过Service访问到Pod中的容器
  - 基础要点
    - Service不会直接运行应用，只负责转发请求
    - Service地址固定，只要不删除，访问地址不会变（解决Pod IP 动态变化的问题）
  - 为什么需要Service？
    - Pod是临时的，会根据需求动态创建、销毁
    - 如果Pod IP 变化，外部访问会失败
    - Service可以将多个Pod的端口映射到一个固定端口，外部可以通过Service访问到多个Pod中的容器
- Deployment（Pod的控制器）
  - 核心定义：用来管理Pod的生命周期，负责Pod的创建、更新、扩容、回滚，不用手动操作Pod，由Deployment自动维护Pod的运行状态
  - 基础要点
    - Deployment会根据配置自动创建、删除、重启Pod
    - 可以设置Pod的数量、重启策略、更新策略等
    - 可以根据Pod的健康状态、资源占用等指标，自动调整Pod的数量
